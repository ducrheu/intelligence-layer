# 找“曾经存在过”的数据：从轻到重的阶梯

用户说“能不能拿到当时的...”时，**先走轻的、先验前提**，不要一上来就上最重的工具（本次会话就因为直接改路径启动浏览器，造成了 953 行 cookie 被删）。

## 第 0 步（最先做，成本最低）：验前提
- 数据是否**真的需要恢复**？源系统（服务器端）还认不认那个凭证/会话？不认的话取回什么都是废纸。
- 用户说的“现在不是这样了”需要**实机确认**（让他打开界面看一眼），不要用推断代替。
- **零风险的外部源先查**：浏览器密码库（`Login Data`）、其它浏览器/PWA 容器、`Snapshots/<版本>/`、应用自己的导出备份。这些都不需要动现行文件。

## 阶梯（按侵入性递增）
| 手段 | 需要 | 能拿到什么 | 风险/前提 |
|---|---|---|---|
| 直接读现行文件 | 无 | 还在的记录 | 被应用独占锁定时必须**先关应用** |
| 应用自带的快照/备份目录 | 无 | 特定几类数据 | 覆盖率低（例：浏览器 `Snapshots/` 不含 `Network/`） |
| SQLite 空闲页考古 | 一份文件拷贝 | 已被 DELETE 但页未重写的行 | 一旦页被重写就没了；**别把列数写死**（schema 会版本迁移） |
| 卷影副本 VSS | 管理员 + 系统保护开启 | 删除前整文件 | 要用户点 UAC；不保证有快照；见本技能 SKILL.md |
| 提权破解应用层加密 | 管理员 + 往安装目录写文件 | 应用私有密钥 | 成功率不保证，动静大，最后再上 |

## 两条铁律
1. **任何改变启动参数/路径/文件的尝试，先复制一份原件到安全位置**，并记住：很多应用发现解不开密文会**直接删行**，一次误启动就能把一个库清空。
2. **验证手段不够时，用最小代价的观察代替推断**：能看就看（让用户在界面上看），不能看就看旁证（日志/历史标题/时间戳/其它客户端），别拍脑袋下“丢了”的结论——本会话曾因为解析器列数写死，得出了错误的“已被覆盖”结论。
