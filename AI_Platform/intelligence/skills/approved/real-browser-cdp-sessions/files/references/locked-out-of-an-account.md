# 用户被锁在自己的账号外（「把旧 cookie / 存的密码拿来登进去」）

## 先定性：他要的是哪一种

| 他要的 | 性质 | 我做什么 |
| --- | --- | --- |
| 把上次的会话 cookie 从 profile 里抠出来重放 | 会话劫持 | 不做 |
| 把浏览器保存的密码解出来拿去登 | 凭证提取 | 不做；给他浏览器自己看密码的那条路 |
| 帮他铺好页面，他自己扫码 / 敲密码 / 过验证码 | 正常协助 | 做 |

## 诊断顺序：先要报错原话

「什么登录方式都不能用」= 拦他的是**服务端账号状态**，不是浏览器。这种状态下拿到密码或 cookie 一样进不去，所以别先折腾 cookie。

| 提示 | 大概率原因 | 出口 |
| --- | --- | --- |
| 账号被封禁 / 违规 | 服务端封号 | 官方申诉，人工审核 |
| 环境异常 / 设备异常 | 风控认定换设备 | 换手机流量、卸载重装 App 再登 |
| 收不到验证码 | 号码不在手上 / 运营商拦截 | 换网络重发；换绑 |
| 手机号未注册 / 不存在 | 被换绑过或号码已注销 | 只能申诉 |
| 要人脸 / 实名核验 | 当初实名不是本人 | 决定能不能找回 |

要问清的三件事：

1. **上次是在哪台设备 / 哪个浏览器登的** —— 那份登录态可能还活着，直接用就行，什么都不用恢复。
2. **手机上的 App 现在还是登录状态吗** —— 是，则扫码即可，无需任何「恢复」。
3. **绑定的手机号现在还能收短信吗** —— 决定走验证码登录还是只能申诉。

## 为什么「抠 cookie」即使做了也白做

1. 会话 token 按小时计，隔天基本已被服务端作废。**用户手上那个浏览器现在打不开登录态，本身就证明那份凭证已废。**
2. 会话绑**设备指纹 + 出口 IP**。灌进另一个 profile 极易触发风控，还可能把号再标记一层异常。
3. Chromium 127+ 的 **App-Bound Encryption**：cookie 的加密密钥（`Local State` 里的 `os_crypt.app_bound_encrypted_key`）由浏览器自身的服务校验调用方，外部进程拿不到；**把 profile 拷到别的目录同样解不开**。这是浏览器专为防这件事做的加固，不是配置问题、不是「换个工具就行」。

（保存的**密码**在 `Login Data` 里仍走老的 DPAPI 方案，用当前用户的 DPAPI 理论上能解 —— 正因为能，才更要明确地不碰。用户要看密码，走浏览器自己的密码管理器 UI，让系统 PIN / 生物识别把关。）

## 正路（按优先级）

1. **浏览器自带密码管理器**：`chrome://settings/passwords` / `edge://settings/passwords` → 找站点 → 「显示」→ 系统要 Windows PIN / 生物识别。密码经用户自己的手。
2. **站点的密码登录模式**：不少平台网页端都有（登录框常见三个页签：验证码登录 / 密码登录 / 扫码登录），**手机不在身边也能登**。我负责切到密码登录页并截图给他。
3. **官方找回 / 申诉**：我帮他整理材料 —— 时间线、常用设备、绑定过的手机号、消费与发布记录，这些是人工审核真正看的。
4. 以后想让我自动登录 → `browser_vault_save_login`（值不进上下文）。

## 只在必要时用的只读诊断

判断「某站点的登录态落在哪个 profile」：把候选 profile 的 `Default/History`（SQLite）**复制出来**再查 —— 开着的浏览器会锁库。Chrome / Edge 的访问时间是 **1601-01-01 起的微秒数**。

**只查目标域名、只用来回答登录态在哪**；不要顺手把用户的全部浏览记录读出来。
